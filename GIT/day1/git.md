# Git & GitHub 핵심 개념 정리

## 1. Git / GitHub 기본 개념
* **Git & GitHub를 사용해야 하는 이유**: 코드의 변경 이력을 체계적으로 추적하여 언제든 이전 상태로 되돌릴 수 있고, 여러 개발자가 동시에 작업하더라도 코드가 덮어씌워지는 사고 없이 안전하게 협업할 수 있기 때문.
* **Git과 GitHub의 차이**: **Git**은 로컬에서 파일의 변경 이력을 기록하고 관리하는 '분산 버전 관리 프로그램'이고, **GitHub**는 Git으로 관리하는 프로젝트 복사본을 클라우드 서버에 올려 공유하고 협업하는 '원격 호스팅 웹 서비스'이다.
* **Repository (저장소)**: 프로젝트의 파일들과 변경 이력이 저장되는 공간으로, 내 컴퓨터에 있는 **로컬 저장소**와 GitHub 서버에 있는 **원격 저장소**로 나뉜다.
* **Commit (커밋)**: 의미 있는 코드 변경 사항들을 하나의 묶음으로 만들어 저장소에 영구적으로 저장하는 작업이자, 그 기록된 버전의 단위이다.
* **Branch (브랜치)**: 기존 원본 코드에 영향을 주지 않고 독립적으로 새로운 기능을 개발하거나 버그를 수정할 수 있도록 분기해 나온 별도의 작업 공간이다.

## 2. Git 기본 명령어
* **`git config`**: Git 사용자의 이름(`user.name`)과 이메일(`user.email`) 등 환경 설정값을 확인하거나 지정할 때 사용하는 명령어.
* **`git init`**: 현재 일반 디렉토리를 Git이 버전을 추적할 수 있는 새로운 로컬 저장소로 초기화(`.git` 폴더 생성)하는 명령어.
* **`git status`**: 작업 디렉토리의 파일들이 수정되었는지, 스테이징 영역에 올라갔는지 등 현재 저장소의 상태를 확인하는 명령어.
* **`git add`**: 작업 디렉토리에서 수정하거나 새로 만든 파일들을 다음 커밋에 포함시키기 위해 스테이징 영역에 올리는 명령어.
* **`git commit`**: 스테이징 영역에 준비된 파일들의 변경 사항을 메시지와 함께 로컬 저장소에 하나의 확정된 버전으로 기록하는 명령어.
* **`git push`**: 로컬 저장소에 기록된 커밋 이력들을 원격 저장소로 업로드하여 반영하는 명령어.
* **`git pull`**: 원격 저장소의 최신 커밋 이력을 내 로컬 저장소로 가져와(`fetch`) 현재 작업 중인 브랜치에 병합(`merge`)하는 명령어.

## 3. Branch (브랜치 관리 및 병합)
* **`git branch` 명령어**: 현재 저장소의 브랜치 목록을 조회하거나 새로운 브랜치를 생성·삭제할 때 사용하며, 브랜치를 이동할 때는 `git switch`(또는 `git checkout`)를 함께 활용한다.
* **브랜치 관리 전략 (Git Flow)**: 역할에 따라 브랜치를 나누어 운영하는 체계적인 협업 방식.
  * **`main`**: 실제 사용자에게 배포되는 가장 안정적인 최종 제품 코드가 유지되는 중심 브랜치.
  * **`develop`**: 다음 출시 버전을 위해 개발 중인 기능들이 하나로 합쳐지는 통합 개발 브랜치.
  * **`feature`**: `develop` 브랜치에서 분기하여 로그인, 결제 등 개별 단위의 새로운 기능을 개발한 뒤 다시 합치는 브랜치.
  * **`release`**: 개발이 완료된 `develop` 브랜치의 코드를 `main`에 최종 배포하기 직전에 QA(품질 테스트)와 마무리 버그 수정을 진행하는 브랜치.
  * **`hotfix`**: 이미 배포된 `main` 브랜치에서 긴급한 장애나 버그가 발생했을 때 이를 즉각 수정하여 빠르게 재배포하기 위한 브랜치.
* **Fast-forward (패스트포워드 병합)**: 분기해 나간 브랜치에만 새로운 커밋이 있고 기준 브랜치에는 아무런 변경이 없을 때, 별도의 병합 커밋을 만들지 않고 기준 브랜치의 포인터만 최신 커밋으로 쭉 이동시키는 병합 방식.
* **3-way merge (3자 병합)**: 기준 브랜치와 분기한 브랜치 양쪽 모두에 새로운 커밋이 생겼을 때, 두 브랜치의 공통 조상(Base) 커밋까지 총 3개의 지점을 비교하여 새로운 '병합 커밋'을 생성해 합치는 방식.
* **Merge conflict (병합 충돌)**: 두 브랜치에서 같은 파일의 같은 줄을 서로 다르게 수정한 뒤 병합을 시도할 때 발생하며, Git이 어느 쪽 코드를 남길지 자동으로 판단할 수 없어 개발자가 직접 코드를 정리하고 다시 커밋해 해결해야 한다.
